# Mini NPU Simulator — 코디세이 미션 3

**AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기.** 입력 패턴과 필터의 같은 위치 원소를 곱하고 누적하는 MAC(Multiply-Accumulate)을 Python 반복문으로 구현했습니다. 실제 NPU 하드웨어가 아니라 CPU에서 원리를 확인하는 콘솔 시뮬레이터입니다.

## 실행 방법

Python **3.8 이상**, 표준 라이브러리만 사용합니다. NumPy·pandas 등 외부 패키지나 설치 명령은 필요 없습니다.

```powershell
cd codyssey-mini-npu
python main.py
```

메뉴 `1`은 3×3 직접 입력, `2`는 제공 `data.json` 분석, `0`은 종료입니다. 앞뒤 공백은 제거하고 잘못된 메뉴는 다시 입력받습니다.

```powershell
python main.py --mode manual
python main.py --mode json
python main.py --mode json --data path/to/data.json --repeats 100
python -m unittest -v
```

기본 데이터 경로는 **main.py 옆 data.json**이므로 다른 작업 폴더에서 실행해도 같습니다. 반복 횟수는 기본 30회, 최소 10회입니다. 분석 자체를 완료하면 종료 코드 0, 파일 읽기 실패·최상위 구조 오류 등으로 분석을 시작할 수 없으면 1을 반환합니다. 개별 패턴의 FAIL은 정상적으로 보고하는 분석 결과이므로 프로그램 종료 코드와 구분합니다.

## 모드 1: 사용자 입력 (3×3)

필터 A 3행 → 필터 B 3행 → 저장한 필터 내용 확인 → 패턴 3행 → 점수·시간·판정 → 3×3 성능 표 순서로 실행합니다. 저장은 프로그램 실행 중의 메모리 행렬 보관을 뜻하며 사용자 입력을 파일에 쓰지는 않습니다.

필터 A에 아래 3줄을 입력합니다.

```text
0 1 0
1 1 1
0 1 0
```

필터 B와 패턴에는 각각 아래 3줄을 입력합니다.

```text
1 0 1
0 1 0
1 0 1
```

실제 확인 결과는 **A 점수 1, B 점수 5, 판정 B**입니다. 시간은 실행 장치와 상황에 따라 바뀝니다. 원본 출력: [manual-x.txt](docs/manual-x.txt).

각 행은 공백으로 구분한 유한 숫자 3개여야 합니다. `1 0`, `1 0 1 0`, `a b c`, 빈 Enter, `nan 0 1`, `inf 0 1`은 안내 후 **그 행만** 다시 입력받습니다. 3개의 유효한 행을 받기 전에는 계산하지 않습니다. 이 행 단위 입력 방식으로 행 수를 고정하고 각 행의 열 수도 검증합니다. 3행보다 더 입력한 내용은 다음 필터/패턴의 입력으로 해석되므로 안내한 단계별로 3행씩 입력해야 합니다. Ctrl+C나 EOF가 발생하면 안내 후 미완성 행렬을 계산하지 않고 종료합니다.

## 모드 2: 제공 data.json 분석

미션 페이지의 첨부 파일 **원본 그대로** 포함했습니다. 기본 필터는 5×5·13×13·25×25이고 패턴은 총 **6개**입니다. 예시 화면의 ‘8개’는 설명용 숫자이며 실제 파일의 개수와 구분합니다. 원본 보존 확인: [data-source.txt](docs/data-source.txt).

```json
{
  "filters": {
    "size_5": {"cross": [[0, 0, 1, 0, 0]], "x": [[1, 0, 0, 0, 1]]}
  },
  "patterns": {
    "size_5_1": {"input": [[1, 0, 0, 0, 1]], "expected": "x"}
  }
}
```

위 예시는 **키 배치만 축약한 설명**입니다. 실제 5×5 데이터는 각 행 5개 숫자로 된 **5행 전체**가 필요하며 위 한 행 예시를 그대로 실행하면 크기 오류로 FAIL 처리됩니다. 제출 파일 `data.json`에는 완전한 행렬이 들어 있습니다.

`size_{N}_{idx}` 키를 정규식으로 검사하고 N에 맞는 `filters.size_N`을 찾습니다. 입력과 두 필터 모두 N×N인지 검증하며, 각 값은 bool·문자열이 아닌 유한 int/float여야 합니다. 누락 필터, 열/행 불일치, 알 수 없는 라벨, 중복 라벨 등은 **해당 케이스 FAIL과 원인**으로 기록하고 나머지는 계속 분석합니다. 잘못된 JSON 문법이나 filters/patterns 자체가 없는 최상위 오류는 별도 ‘분석 오류’로 안내합니다. 원본 파일을 자동 수정하거나 덮어쓰지 않습니다.

### 라벨 정규화

| 위치·입력 | 내부 표준 라벨 |
| --- | --- |
| expected `+`, `Cross`, `cross` | `Cross` |
| expected `x`, `X` | `X` |
| 필터 키 `cross`, `Cross`, `+` | `Cross` |
| 필터 키 `x`, `X` | `X` |

앞뒤 공백과 대소문자를 정리한 뒤 비교합니다. 숫자나 `triangle` 같은 알 수 없는 값은 추측하지 않고 FAIL로 처리합니다. 필터에 `cross`와 `+`를 동시에 넣으면 정규화 후 이름이 같으므로 중복 오류입니다. 내부 기대 라벨은 Cross/X 두 종류이며, `UNDECIDED`는 출력 전용 판정입니다.

### MAC 연산과 epsilon 정책

`score = Σ(pattern[r][c] × filter[r][c])`를 이중 for문으로 계산합니다. 예를 들어 십자가 패턴과 같은 3×3 필터는 5, X 필터와는 1이 나옵니다. 음수·소수도 처리하며 NaN/무한 입력 및 계산 중 수치 범위 초과는 오류로 안내합니다.

`abs(score_a - score_b) < 1e-9`이면 동점입니다. **정확히 1e-9 차이는 동점이 아닙니다** (`<` 사용). 그렇지 않으면 큰 점수의 라벨을 선택합니다. 모드 1은 A/B 또는 `판정 불가 (UNDECIDED)`, 모드 2는 Cross/X/UNDECIDED를 출력합니다. UNDECIDED를 expected에 맞춰 임의로 Cross나 X로 바꾸지 않습니다. 비교는 두 표준 라벨이 같은 경우만 PASS입니다.

## 결과 리포트 — 실패 원인 분석과 시간 복잡도

### 제공 데이터의 실제 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | 정규화 expected | 결과 |
| --- | ---: | ---: | --- | --- | --- |
| size_5_1 | 약 0.90000000000000002 | 약 0.89999999999999991 | UNDECIDED | X | FAIL |
| size_5_2 | 약 8.9 | 약 0.1 | Cross | Cross | PASS |
| size_13_1 | 약 0.3 | 약 14.7 | X | X | PASS |
| size_13_2 | 약 7.4999999999999973 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 약 4.9000000000000004 | 약 4.8999999999999986 | UNDECIDED | X | FAIL |
| size_25_2 | 약 52.9 | 약 0.1 | Cross | Cross | PASS |

**총 6개 / PASS 3개 / FAIL 3개**입니다. 각 실패 케이스 식별자와 사유를 콘솔 마지막에 다시 출력합니다. 원본 전체 출력과 성능 표: [provided-data-run.txt](docs/provided-data-run.txt).

1. 원본 expected의 `+`와 `x`를 그대로 비교하면 Cross/X와 다른 문자열이라 판정이 맞아도 거짓 FAIL이 생깁니다. 정규화로 이 라벨 표현 문제를 제거했습니다.
2. 실제 제공 데이터는 크기별 2개씩 총 6개이며, 각 패턴에서 키로 추출한 N과 행렬 모양이 일치합니다. 원본에는 스키마 오류가 없었습니다.
3. `size_5_1`의 점수 차이는 약 1.11×10⁻¹⁶으로 1e-9보다 작아 동점입니다. expected는 X이므로 FAIL입니다.
4. `size_13_2`의 차이는 약 2.66×10⁻¹⁵이며, expected Cross라도 같은 epsilon 정책에 따라 UNDECIDED/FAIL입니다.
5. `size_25_1`의 차이는 약 1.78×10⁻¹⁵로 역시 UNDECIDED이며 expected X와 달라 FAIL입니다.
6. 이 세 FAIL은 프로그램 중단이나 배열 선택 오류가 아니라 **거의 같은 점수와 기대 라벨을 주어진 동점 규칙으로 비교한 결과**입니다.
7. 단순 `>`만 쓰면 이진 부동소수점 누적 오차가 더 큰 쪽을 우연히 선택할 수 있습니다. epsilon은 그 작은 차이로 판정을 확정하지 않게 합니다.
8. FAIL을 없애려고 expected나 필터를 고치거나 케이스별 답을 하드코딩하지 않았습니다. 분석 보고서에 정직한 실패 원인을 남기는 것이 요구사항입니다.
9. 데이터/스키마 문제는 필터 누락·차원 오류·잘못된 라벨로, 로직 문제는 알려진 3×3 점수(5와 1) 및 순수 MAC 테스트로, 수치 비교 문제는 점수 차이와 epsilon 경계 테스트로 나누어 확인했습니다.
10. 의도적으로 행렬과 라벨을 손상한 별도 검증 데이터에서는 케이스 단위 FAIL 이후에도 다른 패턴이 분석되고 총합이 일치함을 확인했습니다. [schema-errors.txt](docs/schema-errors.txt)에 증거를 보관했습니다.
11. 한 필터의 MAC은 N개 행마다 N개 열을 방문하므로 곱셈 N²번과 누적 덧셈 N²번을 수행합니다. 표의 ‘연산 횟수 N²’는 **MAC 위치 처리 횟수**이며 곱셈과 덧셈을 따로 세면 각각 N²번입니다.
12. 두 필터를 모두 비교하면 MAC 위치 처리는 2N²번입니다. 상수 2를 제외하면 여전히 시간 복잡도 **O(N²)**입니다. 크기에 따라 기하급수/지수적으로 증가하는 알고리즘이 아닙니다.
13. 시간 측정은 `perf_counter_ns()`로 MAC 호출 구간만 측정하고 ns를 1,000,000으로 나눠 ms로 변환합니다. JSON 읽기·입력·출력·행렬 생성·검증은 측정 구간 밖입니다.
14. 각 크기에서 워밍업 1회 뒤 기본 30회를 반복하여 산술 평균을 냅니다. 시간은 실제 측정값이고 문서의 예시값을 출력하는 코드가 아닙니다.
15. 아래 표는 해당 환경에서의 한 실행 결과입니다. N² 증가에 따라 시간이 커지는 경향을 보이지만 작은 행렬에서는 함수 호출·타이머 비용의 비중이 커서 시간 비율이 N² 비율과 정확히 같지는 않습니다.
16. 프로세스 스케줄링, CPU 전원 상태, Python 버전 등에 따라 개별 측정은 변합니다. 반복 횟수를 늘려 재측정할 수 있으며 한 번의 벽시계 측정으로 하드웨어의 절대 성능을 일반화하지 않습니다.
17. MAC 함수의 추가 공간은 누적 합과 인덱스뿐이라 O(1)이고, 입력·필터 보관은 O(N²)입니다. 파일 전체를 `json.load()`로 읽는 분석 모드는 파일 크기에 비례한 메모리도 사용합니다.
18. 실제 NPU는 많은 MAC을 병렬 처리할 수 있지만 이 코드는 CPU의 Python 중첩 루프로 직렬 실행합니다. 성능 표를 NPU 가속 성능으로 해석하지 않습니다.

### 크기별 실제 성능 표

각 크기에서 **MAC 한 필터 호출 30회 평균**, 워밍업 1회 제외입니다. 3×3은 제공 데이터에 없어 생성한 Cross, 나머지는 같은 크기의 생성 Cross 입력과 **제공 파일의 Cross 필터**를 사용합니다. 패턴값에 따라 방문 수를 줄이는 최적화는 사용하지 않습니다.

| 크기 | 평균 시간(ms) | MAC 위치 수 N² |
| --- | ---: | ---: |
| 3×3 | 0.002150000 | 9 |
| 5×5 | 0.004506667 | 25 |
| 13×13 | 0.024990000 | 169 |
| 25×25 | 0.095750000 | 625 |

25×25의 위치 수는 3×3의 약 69.44배, 이 실행의 시간은 약 44.53배였습니다. 고정 오버헤드와 측정 잡음을 감안해 수치 비율과 이중 반복문의 연산 횟수 근거를 함께 해석합니다. 직접 입력 모드의 시간은 A와 B 각각 반복 측정하여 출력하며, 성능 표는 A 한 개를 기준으로 합니다.

## 대형 행렬(1000×1000)의 처리 한계와 최적화 우선순위 — 평가 #19

현재 구현은 미션의 3×3~25×25 데이터에 맞춘 학습용입니다. `Matrix`와 `mac()`는 일반 N×N도 처리하지만, **1000×1000 실행의 처리 시간·최대 메모리는 측정하지 않았으며 해당 크기의 성능을 보장하지 않습니다.** 생성기 `generate_pattern()`는 홀수 크기만 허용하므로 1000×1000은 별도의 실제 입력 행렬을 준비해야 합니다.

### 시간 제약

1000×1000의 MAC 한 번은 위치 **1,000,000개**, 두 필터의 판정은 위치 **2,000,000개**를 처리합니다. 한 필터를 30회 반복 측정하면 워밍업을 제외하고 **30,000,000회**의 곱셈·누적이 필요합니다. 두 필터를 각각 같은 횟수로 측정하면 60,000,000회이며, 최초 판정과 워밍업 비용은 여기에 더해집니다. Python 이중 반복문의 원소 접근·실수 곱셈·덧셈 비용이 누적되므로 체감 대기 시간이 커질 수 있습니다. 25×25 대비 한 MAC의 위치 수는 **1,600배**지만 캐시·메모리 접근·실행 환경이 달라 실제 시간이 정확히 1,600배라고 단정할 수 없습니다. 최소 10회 측정 조건은 유지하되 큰 입력에서는 기본 30회를 무조건 늘리기보다 먼저 10회로 병목을 확인하는 편이 적절합니다.

### 메모리 제약과 불필요한 복사

원소가 1,000,000개인 행렬을 64비트 실수의 연속 버퍼로 보관하면 숫자 본문만 8,000,000 bytes(약 7.63 MiB)이고, 입력과 필터 2개는 본문만 약 22.89 MiB입니다. **이 수치는 현재 Python list 구현의 실제 사용량이 아닙니다.** 현재는 행 리스트·원소 참조·Python 숫자 객체가 추가되고, 행렬 생성 때 새 행 리스트를 만들기 때문에 더 많은 메모리가 필요합니다. 구체적인 객체 크기는 Python 구현과 플랫폼에 따라 달라집니다.

또한 `json.load()`가 전체 파일을 읽고 숫자·리스트 객체를 만든 뒤 `Matrix`로 변환합니다. 변환 중 원본 JSON의 객체 구조와 새 행 리스트가 동시에 존재하고, 원본 document는 분석이 끝날 때까지 유지됩니다. 모든 패턴을 JSON에 넣으면 메모리는 현재 패턴 한 장뿐 아니라 **파일 전체 패턴 수**에 비례해 증가합니다. `analyze()`의 필터 캐시, 생성한 성능 측정용 패턴, 결과 목록도 메모리를 사용합니다. `core.mac()`의 누적 변수 자체는 O(1)이지만, 이것이 프로그램 전체 메모리가 O(1)이라는 뜻은 아닙니다. 메모리가 부족하면 느려지거나 할당 실패·프로세스 종료가 발생할 수 있습니다.

### 우선순위별 개선 계획

아래는 **대형 입력을 지원하도록 확장할 때의 계획**이며 현재 코드에 구현된 최적화는 아닙니다. 외부 라이브러리 없이 표준 라이브러리 범위에서 우선 검토합니다.

| 우선순위 | 최적화 항목 | 적용 지점·기대 효과 | 주의할 점 |
| --- | --- | --- | --- |
| 1 | 입력 한도와 메모리·시간 측정 | 로드 전에 파일 크기·허용 N·패턴 수를 제한하고, 대표 입력으로 시간과 최대 메모리를 먼저 측정 | 제한 기준은 실측 후 정함. `tracemalloc`은 Python 할당 추적이므로 OS 전체 메모리 수치와 구분 |
| 2 | 복사·중간 행렬 회피 | `Matrix` 변환 시 원본과 새 자료구조를 함께 오래 보관하지 않도록 소유권을 정리하고, 패턴별 처리 후 참조 해제 | 곱한 결과 전체를 별도 N×N 배열에 저장하지 않고 현재 MAC처럼 바로 합산. 입력 객체 공유 시 검증 후 외부 변경도 통제 |
| 3 | 패턴 단위 스트리밍 | 필터는 재사용하고 패턴은 한 개씩 읽어 판정·요약한 뒤 해제. 결과도 필요하면 파일에 순차 기록 | 현재 중첩 JSON에 `json.load()`를 그대로 쓰면 스트리밍이 아님. 한 줄에 패턴 하나인 JSONL이나 패턴별 파일 등 입력 포맷·로더 변경 필요 |
| 4 | 연속 저장과 순차 접근 | `array.array('d')` 같은 표준 라이브러리 버퍼로 평탄화해 Python 숫자 객체·원소 참조 비용과 포인터 탐색을 줄임 | list를 평탄화만 하면 Python float 객체 비용이 사라지지 않음. 변환 비용·추가 복사를 연산 시간과 분리 측정 |
| 5 | 행/블록 단위 MAC | 예를 들어 100행 블록씩 입력·필터의 같은 위치를 읽어 부분합을 누적. 밀집 입력과 두 필터의 전체 버퍼가 꼭 필요한지 재검토 | 단순 위치별 곱셈이므로 행 순서 순차 처리가 우선. 블록만 나눠도 O(N²)는 유지되며, 작은 JSON 블록 저장이나 위치 접근 가능한 파일 형식이 필요 |
| 6 | 측정 후 병렬화 검토 | 큰 입력에서 직렬 루프가 실제 병목이면 프로세스 단위 분할을 후보로 검토 | Python 스레드만으로 CPU 루프 가속을 기대하지 않음. 프로세스 전송·자료 복제·시작 비용이 커질 수 있어 가장 나중에 비교 |

블록/스트리밍으로 얻는 핵심 효과는 전체 패턴과 모든 중간값을 동시에 보관하는 일을 피하는 것입니다. 필터 전체를 메모리에 유지하면 여전히 필터당 O(N²) 공간이 들고, 패턴과 두 필터를 모두 블록으로 읽을 수 있는 저장 구조를 만들었을 때에만 작업 버퍼를 블록 크기 수준으로 줄일 수 있습니다. 크기·라벨·유한 숫자 검증도 블록마다 유지하고, EOF에서 전체 행/열 수가 맞는지 확인해야 합니다.

최적화 전후에는 **동일 입력·동일 반복 횟수·동일 측정 구간**으로 MAC 시간과 전체 로드 시간, 최대 메모리를 각각 비교합니다. 블록 부분합이나 병렬 합산은 덧셈 순서를 바꿔 부동소수점 결과가 달라질 수 있으므로 기존 정답·동점·epsilon 경계 테스트를 다시 검증해야 합니다. 데이터 변경이나 expected에 맞춘 판정 변경으로 성능/정확도를 좋게 보이게 하지 않습니다.

## 파일 구조와 책임

```text
main.py           메뉴, 3×3 입력 검증, 출력과 성능/결과 요약
core.py           Matrix, 라벨 정규화, MAC, epsilon 비교, 반복 측정, 패턴 생성
analysis.py       data.json 읽기, 필터/패턴 검증, 케이스 판정과 집계
data.json         제공 원본 (20,738 bytes, 수정하지 않음)
test_simulator.py 정상·실패·경계 조건 테스트 15개
docs/             실제 실행 로그, 테스트 결과, 원본 SHA-256
```

`Matrix`는 N×N 값과 크기를 함께 묶어 `get(row, column)`과 `set(row, column, value)`를 제공합니다. 인덱스는 0부터 시작하며 음수·범위 밖 인덱스는 거절합니다. 행렬 생성과 set은 유한 숫자를 검사합니다. `rows`를 외부에서 직접 수정하면 검증을 우회할 수 있으므로 사용자 값 변경은 set을 사용합니다.

함수와 list만으로도 구현할 수 있지만 Matrix를 사용하면 크기와 검증 규칙을 데이터와 묶어 MAC 호출부에서 일관되게 사용할 수 있습니다. 반대로 MAC·판정·정규화는 자체 상태가 필요 없어 함수로 분리했습니다. 파일 IO는 `load_document()`, 케이스 분석은 `analyze()`, 화면은 main의 책임입니다.

선택 과제인 홀수 크기 Cross/X 패턴 생성기 `generate_pattern()`를 구현하여 3×3 성능 분석과 테스트에 재사용했습니다. 1차원 배열 최적화와 전후 비교는 구현하지 않았으며 해당 최적화를 했다고 주장하지 않습니다.
